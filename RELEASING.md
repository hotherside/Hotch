# Releasing Hotch

This guide describes a maintainer release from a clean checkout. The release version is defined in `Makefile` and checked against the app's development fallback; read it with `make print-version`. Releases require a macOS machine with a compatible Swift toolchain and SDK. Signed distribution also requires the maintainer's own Developer ID and notarization credentials; do not put credentials, certificates, or private keys in the repository or CI logs.

## Prepare

1. Review the changes and update `CHANGELOG.md`.
2. Set the intended version in `Makefile` and the development fallback in `Sources/Hotch/About.swift` to the same value.
   Update `linux/Cargo.toml`, its `hotch` entry in `linux/Cargo.lock`, and `linux/gnome-extension/metadata.json` (`version-name`) as well. Run `python3 linux/tools/check_version.py`; every version must agree. Unreleased changes stay under `Unreleased` in the changelog until a release version is chosen.
3. Run `make check` and review the resulting app on a Mac. Check the version with `make print-version`.
4. Ensure the release notes accurately state supported macOS versions, known provider limitations, and whether the build is signed and notarized.

## Build and package

For a local architecture build, run `make app`. For a universal bundle run `make app-universal`; this builds arm64 and x86_64 separately, then joins them with `lipo`.

To make a signed and notarized release, configure a Developer ID Application identity in the macOS login keychain. Store a `notarytool` credential profile in that keychain using an interactive terminal:

```sh
xcrun notarytool store-credentials hotch --apple-id you@example.com --team-id YOUR_TEAM_ID
```

Enter your Apple app-specific password only when `notarytool` displays its hidden password prompt. Do not add `--password`, paste the password into an AI chat, or put it in a script or environment file. The prompt keeps it out of the command text and process arguments. An app-specific password is a separate, revocable Apple credential used here to authenticate notarization; Hotch does not use it at runtime. Keep it private even if its label is “Hotch.”

If the password was included in a recorded command, chat, or public file, [revoke that password in your Apple Account](https://support.apple.com/en-us/102654), generate a replacement, and repeat the interactive setup. Revoking this release credential prevents future notarization with it; it does not invalidate existing notarized builds or disconnect Hotch's provider accounts.

Then run:

```sh
make signing-status
make release NOTARY_PROFILE=<keychain-profile-name>
```

`make release` builds the universal app, signs and submits it for notarization, staples the ticket to the app and disk image, and runs release verification. It also zips the stapled app for Sparkle (`build/updates/Hotch-X.Y.Z.zip`) and adds the version to `docs/appcast.xml`; see [In-app updates](#in-app-updates-macos). It will fail if the signing identity or profile is missing. If signing is unavailable, distribute source or clearly label any app bundle as an unsigned local build; do not imply notarization.

The Makefile contains additional packaging targets for maintainers (`make dmg`, `make verify-release`). Review its prerequisites before using release-only targets. Never commit local signing material or generated release artifacts unless a repository policy explicitly calls for them.

## In-app updates (macOS)

Hotch 2.4.0 and later update themselves with [Sparkle](https://sparkle-project.org). Each Mac release adds an entry to the appcast, a public list of versions at `FEED_URL` in the `Makefile` (`https://hotherside.com/hotch/appcast.xml`). Shipped apps ask that address forever, so it must never change. The committed copy is `docs/appcast.xml`; the `Appcast` workflow publishes that one file to GitHub Pages whenever it changes on `main`. The update itself is `Hotch-X.Y.Z.zip`, a release asset beside the DMG.

### The signing key

Updates are signed with an EdDSA key generated by Sparkle's `generate_keys --account hotch`. Its private half lives only in the maintainer's login Keychain, as *Private key for signing Sparkle updates* (account `hotch`). The public half is `SPARKLE_PUBLIC_KEY` in the `Makefile` and ships in every app. Shipped apps refuse an update signed with any other key, so **losing the private key means existing users can never be updated again**. Leaking it would let someone sign an update that Hotch accepts.

Back it up once, from a terminal:

```sh
.build/artifacts/sparkle/Sparkle/bin/generate_keys --account hotch -x hotch-sparkle-key.txt
```

Store the file's contents in your password manager, then delete the file. To sign on another Mac, import it there with `generate_keys --account hotch -f <file>` and delete the file again. Never commit the key, paste it into a chat or issue, or pass it on a command line. The first `generate_appcast` run asks for Keychain access to the key; allow it.

### Each release

1. Write the release's `## X.Y.Z` section in `CHANGELOG.md` for Mac users: `make appcast` copies it verbatim into the update window as Markdown, and fails if it is missing.
2. Run `make release NOTARY_PROFILE=<profile>`. After verification it zips the stapled app into `build/updates/` and runs `generate_appcast`, which signs the zip and writes the entry into `docs/appcast.xml`, pointing at `https://github.com/hotherside/Hotch/releases/download/vX.Y.Z/Hotch-X.Y.Z.zip`.
3. Create the GitHub release with the tag `vX.Y.Z` (the appcast URL depends on it) and attach both `build/dist/Hotch-X.Y.Z.dmg` and `build/updates/Hotch-X.Y.Z.zip`. Publish it and check that the zip URL downloads.
4. Only then publish the appcast: merge the commit that updates `docs/appcast.xml` into `main`. The `Appcast` workflow checks that every download the feed names exists, then deploys the file to GitHub Pages. It refuses an appcast whose zip is not uploaded yet, because that would make every user's update fail.
5. Check `curl -sL <FEED_URL> | grep sparkle:version`, then use **Check for Updates…** on a Mac running the previous version.

### Releases with no macOS changes

Versions stay in lockstep across macOS and Linux, so some releases change only Linux. Run `make release NOTARY_PROFILE=<profile> APPCAST=skip`: the DMG is built and notarised as usual so the download matches the version, but no appcast entry is added, and Mac users are not asked to install an identical app. Attach only the DMG and leave `docs/appcast.xml` alone. The next release with Mac changes is offered to everyone, whichever of the two they have.

### The first Sparkle release

Hosting the feed has to work before 2.4.0 is built, because the address is compiled into every copy:

- [ ] Set `FEED_URL` in the `Makefile` to the final address, and update the address in `SHARING.md`, `README.md` and this file to match.
- [ ] In the repository's **Settings → Pages**, set the source to **GitHub Actions**.
- [ ] In the GitHub account's **Settings → Pages**, add `hotherside.com` as a verified domain, and create the TXT record it asks for at GoDaddy. This stops anyone else claiming a `hotherside.com` subdomain on GitHub Pages if the site is ever switched off while its DNS record remains.
- [ ] At GoDaddy, add a CNAME record `hotch` → `hotherside.github.io`, then enter `hotch.hotherside.com` as the custom domain in the repository's Pages settings (only if the feed is on that subdomain).
- [ ] Once GitHub has issued the certificate, tick **Enforce HTTPS**. Before the first appcast exists, `curl -I https://hotch.hotherside.com/` should answer from GitHub with no certificate error.
- [ ] After the 2.4.0 appcast is merged and the workflow has run, `curl -I <FEED_URL>` must return 200 with no certificate error. Fix it before announcing 2.4.0.

Hotch 2.2.0 and 2.3.0 have no updater. The 2.4.0 release notes must tell those users to download 2.4.0 from the release page once; every later version arrives in the app.

Before shipping 2.4.0, check Backpack across an update by hand; the local test could not, because approving the helper needs you at System Settings. With two Developer ID builds of the real bundle ID pointing at a local feed (below): install the older in Applications, approve the helper and run a Backpack session; update through **Check for Updates…**; then confirm that System Settings → General → Login Items & Extensions still allows Hotch, that the Backpack card says Ready rather than asking for approval, and that a new session starts. `sudo launchctl print system/com.hojaejung.hotch.backpack` should show the helper's program inside the updated bundle and a pid started after the update.

### Testing an update locally

Build a test copy with its own bundle ID, a localhost feed and a throwaway key, so neither your preferences nor the release key are involved (the support folder is shared, so back up `~/Library/Application Support/Hotch/focus-log.json`):

```sh
make app BUNDLE_ID=com.hojaejung.hotch.updatetest FEED_URL=http://127.0.0.1:8765/appcast.xml SPARKLE_PUBLIC_KEY=<test public key>
```

Copy the bundle twice, raise `CFBundleShortVersionString` and `CFBundleVersion` in the second copy and re-sign it with `codesign --force --options runtime --timestamp -s "<Developer ID>"`. Zip the newer copy with `ditto -c -k --sequesterRsrc --keepParent` into a folder, then add it to a test appcast there with `make appcast VERSION=<newer> UPDATE_ZIP=<zip> APPCAST_FILE=<folder>/appcast.xml RELEASE_URL=http://127.0.0.1:8765/ SPARKLE_KEY_FILE=<test private key file> CHANGELOG=<notes>`. The key file holds the base64 32-byte Ed25519 seed. Serve the folder with `python3 -m http.server 8765 --bind 127.0.0.1 --directory <folder>`, open the older copy and use **Check for Updates…**. Delete the `com.hojaejung.hotch.updatetest` preferences afterwards.

## Publish

Review the DMG on a clean macOS account or test machine. Confirm the app opens, provider connection steps match current behavior, and privacy notes remain accurate. Publish the release notes and artifacts in the repository's Releases interface, attach checksums if useful, and verify the downloaded artifact after upload. For a Mac release, attach the update zip too and publish the appcast last, as described above. Do not publish credentials, local logs, or user data.

## Experimental Linux assets

The `Linux release assets` workflow runs when a release is published. It checks out that release's tag, requires it to match all source versions, tests native amd64 and arm64 builds, and attaches two `.deb` packages, a GNOME extension ZIP, and `SHA256SUMS-linux.txt` to the existing release. Its write permission is limited to the final upload job. It does not create a release, tag, DMG or notarization submission. To retry for an existing release, run it manually with that release tag.

Before publishing, follow the [Linux desktop validation checklist](linux/README.md#desktop-validation) on a supported GNOME desktop. CI verifies parsers, state transitions, extension lifecycle with API doubles, CLI fixtures, version alignment and package contents; it does not certify GNOME rendering, Wayland interactions or a live provider account. State that limitation and the remaining platform gaps in the release notes, credit Simon (@sire6) for the original port, and label Linux downloads experimental.

For local Linux packaging:

```sh
python3 linux/tools/check_version.py
cd linux
cargo test --locked
cargo build --release --locked
node --test tests/*.test.mjs
cargo install cargo-deb --locked
cargo deb --no-build
python3 tools/package_extension.py
```

Install the `.deb` on the architecture it was built for and verify the downloaded files against the Linux checksums. Ubuntu 24.04 or newer is the binary build baseline; the GNOME frontend specifically requires Shell 48, 49 or 50. The extension ZIP alone still requires the matching `hotch` binary. Keep Linux distribution separate from Apple's signing/notarization claims.
